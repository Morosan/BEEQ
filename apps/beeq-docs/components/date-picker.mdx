Date pickers provide a guided way to enter dates through a calendar interface. They reduce ambiguity, prevent formatting mistakes, and make it easier to choose a single date, a range, or multiple dates depending on the task.

<Note>
  Use a date picker when the interface benefits from visual date selection or date validation. If users need to enter very flexible freeform dates or work with a tiny, predictable set of choices, a simpler input or select may be more appropriate.
</Note>

## When to use

<CardGroup cols={2}>
  <Card>
    <span className="flex items-center mr-2 text-lg font-medium" role="heading">
      <Icon className="mr-2" icon="thumbs-up" iconType="solid" size={20} color="var(--bq-stroke--success)" />
      Use date pickers when
    </span>
    - Users need to select a specific date with high accuracy
    - A calendar view makes the choice faster than typing
    - You need to limit dates with min/max rules or disabled dates
    - The task involves travel dates, appointments, deadlines, or availability
  </Card>
  <Card>
    <span className="flex items-center mr-2 text-lg font-medium" role="heading">
      <Icon className="mr-2" icon="thumbs-down" iconType="solid" size={20} color="var(--bq-stroke--danger)" />
      Do not use date pickers when
    </span>
    - The date can be entered more efficiently with a simple text field
    - The range of valid dates is so small that a select or radio group is clearer
    - Users need to enter partial, approximate, or highly flexible date values
    - The interaction would be unnecessarily heavy for the task
  </Card>
</CardGroup>

The date picker combines an input trigger with a calendar panel. Keep labels clear, use placeholder text only as supplementary guidance, and make sure the selected value format matches the user's locale expectations.

| Part | Element | Description |
|---|---|---|
| **1** | Label | Describes what date the field is asking for (`label` slot) |
| **2** | Input control | The text field users focus, type into, or use to open the calendar |
| **3** | Suffix icon | Calendar affordance that signals date selection and panel access |
| **4** | Calendar panel | Dropdown surface containing the date selection UI |
| **5** | Month navigation | Previous/next controls for moving through months |
| **6** | Day grid | The selectable day cells, including today, selected, disabled, and range states |

## Accessibility

- **Keyboard access** - users should be able to focus the input with <kbd>Tab</kbd>, open the calendar, navigate dates, and close the panel without a pointer.
- **Clear labeling** - always provide a visible label or an equivalent accessible name so screen reader users understand the purpose of the date field.
- **Color is not enough** - selected, disabled, warning, and error states should never rely on color alone. Validation messages and state changes must remain understandable in text.
- **Validation feedback** - when the date is required or invalid, provide a clear error message and pair it with `validation-status="error"`.
- **Locale expectations** - ensure the displayed and accepted date format matches user expectations for the product's locale to reduce confusion and entry errors.
